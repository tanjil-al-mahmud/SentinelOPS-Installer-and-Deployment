# Running the installer on Windows

The Windows build lives under [`windows/`](../windows/) and is a native
PowerShell port of the shell installer. It exposes the same commands, writes the
same `installer.env`, uses the same phase markers and produces the same
deployment — the containers it starts are identical, because Docker Desktop runs
them in a Linux VM either way.

```powershell
# From a checkout
.\windows\bin\sentinel-ops.ps1 install

# Non-interactive, accept every default (localhost endpoints)
.\windows\bin\sentinel-ops.ps1 install -Yes

# After installation, on PATH (open a new terminal first)
sentinel-ops status
sentinel-ops credentials -Show
```

Targets Windows PowerShell 5.1 as well as PowerShell 7, so a stock Windows
Server host needs nothing installed first.

---

## Before you install

**Windows 10 1809 / Windows 11, or Windows Server 2019+.** Older builds cannot
run a supported Docker Desktop.

**Docker Desktop**, in Linux-container mode, with the WSL2 backend. The
installer checks all three and refuses to continue in Windows-container mode
rather than failing later with a confusing image error.

**Administrator is not required.** The shell installer demands root; that is the
wrong test on Windows, where a standard user can write to `C:\SentinelOps`
perfectly well and only a machine-wide `PATH` entry genuinely needs elevation.
The Windows build therefore checks whether the chosen directory is *writable*
and adapts:

| Running as | Install directory | `PATH` updated |
|---|---|---|
| Administrator | `C:\SentinelOps` | Machine |
| Standard user | `C:\SentinelOps` (or `-Dir <path>`) | User |

**Deploy key.** Same as on Linux — the application repository is private. Put
the private key at `.\deploy_key` next to the installer, or at
`<install-dir>\deploy_key`. The installer copies it into `config\deploy_key`,
locks it down with `icacls`, and normalises CRLF line endings (a key saved on
Windows otherwise makes OpenSSH fail with a misleading "invalid format").

## Where the Windows build deliberately differs

Five divergences are not stylistic. Each exists because the Linux approach
cannot work here.

### 1. Postgres and Storage run on named volumes, not bind mounts

Upstream's compose file bind-mounts two paths from the host:

```yaml
./volumes/db/data:/var/lib/postgresql/data
./volumes/storage:/var/lib/storage
```

On Linux that is fine. On Docker Desktop those paths cross the Windows/Linux
filesystem boundary, which cannot represent Unix ownership or mode bits.
Postgres refuses to start on a data directory it cannot `chmod 0700`, and the
Storage API — which runs unprivileged — cannot write to its volume either.

The installer generates `supabase/docker-compose.windows.yml`, which moves those
two targets onto Docker-managed named volumes living inside the Linux VM:

```yaml
services:
  db:
    volumes:
      - sentinelops-db-data:/var/lib/postgresql/data:Z
  storage:
    volumes:
      - sentinelops-storage-data:/var/lib/storage:z
  imgproxy:
    volumes:
      - sentinelops-storage-data:/var/lib/storage:z
```

Compose merges service volume lists keyed on the container-side target, so
naming the same target *replaces* the bind mount rather than adding a second
one. Every other bind mount (SQL init scripts, envoy config, edge functions) is
read-only or root-owned and is left alone — which is what still lets
`sentinel-ops` deploy edge functions by writing to a Windows directory.

> **Consequence:** the database no longer lives under `supabase\volumes\db\data`.
> It is a Docker volume. `sentinel-ops backup` is the supported way to get the
> data out, and `docker volume ls` will show it.

### 2. Compose files are passed with explicit `-f`, not `COMPOSE_FILE`

The shell build relies on `COMPOSE_FILE` inside `supabase/.env` so that
upstream's `run.sh` overlays keep working. Two problems on Windows:

- The `COMPOSE_FILE` separator is `;` here, not `:` — a `:` would split
  `C:\SentinelOps\...` in half. **The shell build writes `:` unconditionally**,
  so its overlay handling is Windows-hostile by construction.
- Relying on Compose's `--env-file` ordering for something this load-bearing is
  fragile.

The Windows build computes the file list itself and passes
`-f docker-compose.yml [-f docker-compose.logs.yml] -f docker-compose.windows.yml`
on every invocation. The Windows overlay is always last, so it always wins.

### 3. Supabase is staged by sparse checkout, never `setup.sh`

The shell build prefers Supabase's official `setup.sh` and falls back to a
sparse checkout of `docker/`. Windows has no POSIX shell to run `setup.sh` with,
so the fallback is the only path. Everything `setup.sh` would have generated —
the JWT secret, the signed API keys, every other secret — is generated by the
installer instead.

JWT signing uses .NET `HMACSHA256` rather than `openssl dgst`; it is verified
against the RFC 7515 HS256 reference vector.

### 4. Secrets, HTTP and JSON come from .NET

There is no `curl`, `openssl` or `jq` on Windows and no package that reliably
supplies all three. The port uses `RandomNumberGenerator`, `HttpWebRequest` and
`HMACSHA256` instead, so the prerequisite list shrinks to **git** and **ssh**
(the latter enabled as a Windows optional feature when missing).

### 5. SQL goes in by `docker cp`, dumps come out by OS-level redirect

The shell build pipes SQL into `docker exec -i psql` and redirects `pg_dumpall`
into a file. Neither is safe in PowerShell 5.1, whose text pipeline re-encodes
redirected output as UTF-16 and would corrupt every dump. So:

- SQL in: written to a temp file (UTF-8, LF), `docker cp`'d into the container,
  run with `psql -f`.
- Dumps out: `Start-Process -RedirectStandardOutput`, which redirects at the OS
  level and never touches PowerShell's pipeline.

Every file the installer writes goes through one helper that forces **UTF-8
without BOM and LF endings** — a BOM on the first line of an env file becomes
part of the first variable's name inside the container.

### 6. `ssh-keyscan` is chosen, not assumed

The `ssh-keyscan.exe` in `C:\Windows\System32\OpenSSH` is frequently too old to
negotiate with GitHub — it cannot do `sntrup761x25519-sha512@openssh.com` — and
returns **no keys while still exiting successfully**. Git for Windows bundles a
current build, so the installer tries each candidate in turn and keeps the first
that yields a real host-key line.

It also validates the result: only lines shaped `<host> <keytype> <base64>` are
written. Filtering on "not a comment" is not enough, because a failing
`ssh-keyscan` prints diagnostics that are neither, and writing those produces a
`known_hosts` that parses but contains no usable key — surfacing much later as
an unexplained `Host key verification failed`.

If no candidate produces a key, the installer falls back to
`StrictHostKeyChecking=accept-new` rather than writing a file that would make
strict checking fail against every host.

## File permissions

`chmod 600` has no direct equivalent, so the installer calls `icacls` to break
inheritance and grant the file to SYSTEM, Administrators and the current user
only. Principals are named by SID, so it works on non-English Windows.

For directories the grant carries `(OI)(CI)`. Without those flags the grant
applies to the directory object alone, and with inheritance already broken
nothing — not even the owner — can create files inside it.

## Known limitations

- **`sentinel-ops logs -f` needs Ctrl-C to stop**, as on Linux.
- **Docker Desktop must be running.** There is no `systemctl` equivalent; the
  installer starts Docker Desktop and waits up to three minutes for the engine,
  but it cannot enable it as a boot service. Turn on *Start Docker Desktop when
  you sign in* for unattended hosts.
- **`FRONTEND_BUILD_MODE=host` needs Node.js on the machine.** The default
  `docker` mode builds inside the image and needs nothing.
- **Restore is not transactional.** A `pg_dumpall` script contains `\connect`
  commands spanning several databases, so it cannot run inside a single
  transaction — the same is true on Linux.
